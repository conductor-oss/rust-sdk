Wave 8 — Parity gaps found in the 2026-09-17 full-source review (python-sdk vs rust-sdk, verified file-by-file, not from memory). Ordered by real-world impact; each item is independent unless noted.

- [x] **Worker liveness / stall detection** — python's `runtime/_liveness.py` has two mechanisms; both handled (plus the recovery mechanism, decided N/A):
  - [x] `ServerLivenessMonitor` equivalent: `AgentHandle::join`/`join_with_options` periodically fetch the full workflow (`WorkflowClient::get_workflow(execution_id, include_tasks=true)`) and detect `SCHEDULED` tasks stuck at `poll_count == 0` past a stall threshold (default 30s, checked every 10s -- see `src/agents/liveness.rs`). Surfaces as `ConductorError::WorkerStall` (carrying the stalled task list) under `StallPolicy::Raise`, or a `tracing::warn!` under the default `StallPolicy::Warn`. Deliberately workflow-scoped rather than domain-scoped -- see `liveness.rs`'s module doc for why (this crate has no per-execution worker domain to scope by, unlike python).
  - [x] `LocalLivenessCheck` equivalent: implemented as `TaskHandler::verify_workers_started(timeout)` (`src/worker/task_handler.rs`) -- deliberately not agent-specific, since the underlying problem ("registered a worker, but it never actually started polling") applies equally to plain non-agent `TaskHandler` usage. Not a literal port: python's real risk is `fork()` failing or an exception being swallowed during OS-subprocess bootstrap, checked via `p.is_alive()`; this crate's workers are `tokio::spawn`ed futures in the same process, where spawning itself essentially never fails silently the way `fork()` can, so the rust-native risk is instead "did this worker's task actually reach and complete its first real poll" (catches an early panic during setup, or a spawned task that's starved and never reaches the network call). Built on a new `TaskRunner::poll_attempt_count()` counter (incremented right after each real `batch_poll` call, success or failure) plus each spawned task's `JoinHandle::is_finished()`, polled every 50ms until every registered worker clears both checks or `timeout` elapses. New `AgentRuntime::task_handler()` accessor so agent callers can call it right after `serve`/`resume` -- not auto-wired into either, so this doesn't change their existing behavior/signature; it's an explicit, opt-in call. **Surprising finding that shaped this design**: python's own `LocalLivenessCheck` is unreachable dead code today -- defined in `_liveness.py`, but never called from `runtime.py`/`worker_manager.py` anywhere in python-sdk, has no config field wired up (`liveness_startup_timeout_seconds` appears only in its own docstring, not in `AgentConfig`), and no test covers it (unlike `ServerLivenessMonitor`, which has a real call site, a real config field, and its own test file). This wasn't "port an existing python behavior" -- there was no real behavior to port -- so this is the rust-native version of the same underlying safety net the checklist asked for, built and wired up for real.
  - [x] `WorkerRestarter` (SIGKILL + respawn-on-monitor recovery): decided N/A, documented in `liveness.rs`'s module doc -- depends on python's `TaskHandler(monitor_processes=True)` OS-process supervisor, which rust's tokio-task-per-worker model has no equivalent of. Not silently skipped: the decision and reasoning are on record, just not implemented.
- [x] **`AgentRuntime::resume(execution_id, agent)`** — reattach to an existing execution after a process restart. `src/agents/runtime.rs`. Simpler than python's version: since this crate's worker registration has no per-execution domain concept at all (see Wave 8's liveness item above), there's no `task_to_domain` extraction step needed -- `resume` just calls the same `register_agent_workers`/`task_handler.start()` `serve()` already uses, then wraps the given `execution_id` in an `AgentHandle`. Also fixed `serve()`'s doc comment, which incorrectly claimed it blocks for the runners' whole lifetime -- `TaskHandler::start()` only blocks long enough to spawn them.
- [x] **Agent testing/eval framework** — `src/agents/testing.rs`: ported the core, LLM-free slice -- `mock_run`/`ScriptedEvent` (auto-executes a matching tool's real handler, or takes an explicit scripted result) and the fluent `expect(result)` assertion API (`completed`/`failed`/`no_errors`/`used_tool`/`used_tool_with_args`/`did_not_use_tool`/`output_contains`). Required extending `AgentResult` with a new `tool_calls: Vec<ToolCallRecord>` field (empty on a live-poll result -- still no extraction path there, same as every other field the `result.rs` module doc already lists as deliberately unpopulated; real on a `mock_run`-built one). `ScriptedEvent` only covers tool-call/result/done/error, narrower than python's 10-variant `MockEvent` (`THINKING`/`HANDOFF`/`GUARDRAIL_PASS`/`GUARDRAIL_FAIL`/`MESSAGE`/`WAITING` too) -- confirmed rust's real `AgentEvent`/SSE parsing only recognizes 5 wire event kinds today, so those extra `MockEvent` kinds have no real counterpart to script against yet. **Still not ported, separate follow-ups:** record/replay (`recording.py`), LLM-judge semantic assertions (`semantic.py` -- needs an LLM client this crate doesn't have), per-strategy structural validators (`strategy_validators.py`), the LLM-backed correctness eval runner (`eval_runner.py`). The pytest plugin (`pytest_plugin.py`) is N/A as designed -- `cargo test` needs no equivalent.
- [x] **Missing `TaskType` variants**: `GenerateImage` (`GENERATE_IMAGE`), `GenerateAudio` (`GENERATE_AUDIO`), `LlmSearchEmbeddings` (`LLM_SEARCH_EMBEDDINGS`) — `src/models/workflow_def.rs`. Added the enum variants plus `WorkflowTask::generate_image`/`generate_audio`/`llm_search_embeddings` constructors (baking in python's exact default values -- `1024x1024`, `n=1`, `outputFormat="png"` for images) and their optional-field builders (`with_size`/`with_style`/`with_weight`/`with_image_dimensions`/`with_n`/`with_output_format`/`with_text`/`with_voice`/`with_speed`/`with_response_format`/`with_prompt`/`with_dimensions`), reusing the existing generic `with_namespace`/`with_max_results`/`with_embedding_model` builders where the field was already shared with `llm_search_index`.
- [x] **`ServiceRegistryClient`** — gRPC/proto service registry + circuit-breaker management. `src/client/service_registry_client.rs` + new `src/models/service_registry.rs` (`ServiceRegistry`/`ServiceMethod`/`ProtoRegistryEntry`/`CircuitBreakerTransitionResponse`/`RequestParam`/`ServiceRegistryConfig`/`CircuitBreakerConfig`), matching all 14 methods of python's `service_registry_client.py` plus its `is_circuit_breaker_open` convenience (its other convenience, `get_queue_sizes_for_all_tasks`, is a pre-existing, unrelated method on `TaskClient::get_queue_sizes` -- not part of this client). Verified the exact REST mapping against python's generated `service_registry_resource_api.py` rather than guessing, including the two query-param endpoints (`remove_method`'s `serviceName`/`method`/`methodType`, `discover`'s `create`). `get_proto_data`/`set_proto_data` needed new raw-bytes support on `ApiClient` (`get_bytes`/`post_bytes_no_response`) since every existing method assumed a JSON body -- proto file contents are opaque binary. Wiremock tests in `tests/service_registry_client_tests.rs` cover a representative slice (not all 14 methods) including a proto-data raw-bytes round trip and both query-param endpoints.
- [x] **Real LangChain/LangGraph adapter** — decided, documented in `docs/agents/framework-support.md` (re-checked 2026-09-17), not implemented as code. LangGraph: `GraphAgentDef` (`src/agents/graph.rs`, already shipped) remains the intentional Rust-native alternative — the tiny, brand-new `langgraph` crate (~1.2K downloads) doesn't rise to "adopted." LangChain: re-verified crates.io download counts and found the doc's old "no dominant Rust equivalent" premise stale — `rig`/`rig-agent` is now genuinely dominant (~2.8M all-time downloads) — but its `Agent` type still can't be adapted via the existing `FrameworkAgent` trait: tool discovery is `async`+prompt-dependent and there's no plain model-string getter, only an opaque `ModelHandle`. Same "passthrough only" situation as the Claude Agent SDK, not a `FrameworkAgent`-shaped gap. No adapter written; revisit as a passthrough adapter if a concrete user asks.
- [x] **`GPTAssistantAgent`** (OpenAI Assistants API wrapper, python's `ext.py`) — decided: will not be ported. The Assistants API it wraps (`client.beta.assistants.*`/`client.beta.threads.*`) was fully sunset by OpenAI on 2026-08-26 (announced 2025-08-26, one year's notice, no extension) -- every endpoint `_AssistantCall` calls (`/v1/assistants`, `/v1/threads`, and related) now returns errors unconditionally, permanently. This is true of python's `GPTAssistantAgent` too as it stands today, not just a hypothetical rust port. Porting a wrapper for an API that no longer exists would ship a feature that fails 100% of the time it's invoked -- strictly worse than the earlier LangChain-crate finding (where the target at least existed, just wasn't adopted). No architectural gap either way: `GPTAssistantAgent` was never a framework-adapter case needing new machinery -- it's just a native `Agent`/`AgentDef` with `max_turns=1` and one custom tool, everything `AgentDef::with_tool`/`ToolDef::function` already supports today. If OpenAI's replacement (the Responses API) is ever worth wrapping the same way, that's new scope, not this item -- not decided here.
- [x] **`AgentRuntime::deploy(..., schedules=[...])`** — new `AgentRuntime::deploy_with_schedules(agent, schedules: Option<&[Schedule]>)` (`src/agents/runtime.rs`), calling `deploy()` then reconciling via the existing `SchedulerClient`. Rust's `deploy()` already only takes one agent at a time, so python's runtime "requires exactly one agent" check has no equivalent -- the signature already guarantees it. New `src/agents/schedule.rs` ports python's `conductor.client.ai.schedule` (`Schedule`/`ScheduleInfo`/`reconcile`'s tri-state `None`=leave alone / `Some(&[])`=purge all / `Some(non-empty)`=upsert+prune semantics), much smaller than python's version since there's exactly one concrete `WorkflowSchedule` shape here (no duck-typed-client dict/model dual-reading layer to port). Along the way, found and fixed two real wire-format gaps in `src/models/schedule.rs` by checking `WorkflowSchedule.java` directly: missing `description`/`pausedReason`/`nextRunTime` fields, and `update_time` was serializing as `updateTime` instead of the server's actual `updatedTime`.
- [x] **Typed LLM/vector-DB integration convenience layer** — new `AiOrchestrator` (`src/client/ai_orchestrator.rs`) wrapping the existing `IntegrationClient`/`PromptClient`, plus `LlmProvider`/`VectorDb`/`IntegrationConfig` + 4 concrete configs (`WeaviateConfig`/`OpenAiConfig`/`AzureOpenAiConfig`/`PineconeConfig`) in `src/models/ai_integration.rs`, matching python's `AIOrchestrator`/`LLMProvider`/`VectorDB`/`IntegrationConfig`. `add_ai_integration`/`add_vector_store`'s exists-or-overwrite check reuses the same not-found-tolerant pattern already established by `MetadataClient::task_def_exists`/`workflow_def_exists`. Two things python itself never uses ported as dead: `prompt_test_workflow_name` (stored, never read anywhere in python-sdk) and `test_prompt_template`'s `max_tokens` param (never forwarded to the actual request). Config value shapes (e.g. `PineconeConfig`'s `projectName` vs. `api_key` casing inconsistency) are ported byte-for-byte, since the server stores these as an opaque per-provider map with no single canonical schema to "fix" against.
- [x] **Automatic worker/agent discovery** — decided: removed the unused `inventory` dependency from `Cargo.toml` rather than wiring it up. Confirmed via a whole-repo grep (not just `src/`) that it had zero real uses anywhere -- `examples/sdk_playback_33_external_workers.rs`'s hit was a `check_inventory` tool name, an unrelated false positive. Documented the reasoning on `TaskHandler::add_worker` itself: python's package-scanning discovery exists because python has no compile-time registry to lean on, but Rust callers already write out every `TaskDef`/`AgentDef`/`ToolDef` at a well-typed call site, and `inventory::submit!`-based collection has a real sharp edge (registrations silently drop if the registering crate isn't a *direct* dependency of the final binary, depending on linker dead-code elimination) that explicit registration has no equivalent risk for.
- [x] **Claude model alias resolution** — new `resolve_claude_code_model` free function in `src/agents/claude_agent_sdk.rs`, matching python's `claude_code.py` alias table (`"opus"` → `"claude-opus-4-6"`, `"sonnet"` → `"claude-sonnet-4-6"`, `"haiku"` → `"claude-haiku-4-5"`) and its empty-string/unknown-alias passthrough semantics exactly. Added as a new `ClaudeAgentSdkOptions::with_model_alias` builder method rather than changing `with_model`'s existing behavior -- `with_model` stays a literal, unambiguous passthrough (already covered by existing tests asserting exact-value pass-through), and this crate has no `AgentDef.model = "claude-code/opus"` slash-prefixed dispatch convention the way python does (rust's `AgentDef.model` resolves server-side, not client-side), so there was no existing call site to retrofit -- just the alias table itself, ready for whenever/if such a convention is added.
- [x] **`AgentEvent` has fewer variants than python's real stream** — investigated by reading the real server source directly (`AgentSSEEvent.java`, `AgentEventListener.java`, `AgentHumanTask.java` in `~/Code/conductor-oss/conductor`), not just python. Finding was worse than the checklist item assumed: this wasn't just missing coverage. Two of the previously-shipped 5 variants (`Message`/`Progress`) don't correspond to any real server event at all -- there's no `AgentSSEEvent` factory or emit call site for either, so they were never reachable against a real server. Two more (`Waiting`, `Error`) had the *wrong field shape* -- the real `waiting` event carries a single freeform `pendingTool` map, not top-level `tool_name`/`args`; the real `error` event carries `content`/`toolName`, never a field named `error`/`message`. Fixed `src/agents/stream.rs`'s `AgentEvent` to the verified real 12-variant set (`Thinking`/`ToolCall`/`ToolResult`/`Handoff`/`Waiting`/`GuardrailPass`/`GuardrailFail`/`Error`/`Done`/`ContextCondensed`/`SubagentStart`/`SubagentStop`) with exact field shapes from the real DTO -- including `ContextCondensed`/`SubagentStart`/`SubagentStop`, which aren't even in python's own `EventType` enum, so this now exceeds python's coverage rather than just matching it. Updated the stale example code in `docs/agents/rust-sdk-design.md`/`parity-plan.md` to match. Known, documented, not-fixed-here limitation: no `Unknown`/catch-all variant, so a future 13th server event kind would still error out `AgentStream::next` rather than degrading gracefully -- pre-existing property of this design, not newly introduced.

Confirmed deliberately N/A (solve python-only problems): `worker_isolation.py` (process/thread mode) and `_worker_entries.py` (spawn-pickling safety) — both multiprocessing/GIL-specific; `async_task_runner.py` — exists only because python workers can be sync *or* async, rust is uniformly async already; the legacy (pre-harmonization) metrics collector — rust is unreleased, so only the canonical metric set applies (see METRICS.md).
